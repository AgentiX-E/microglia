# R8.3b — the dev split, measured rather than declared unreachable

## Why this file exists

R8.3 closed with a sentence that was true about the sandbox and false about the project: "a genuine
reproduction needs the dev split (n=1,534), which this environment cannot download". The sandbox
cannot reach `huggingface.co`, and that was measured. The dataset is not on `huggingface.co`. It is
on the vendor's CDN, `bird-bench.oss-cn-beijing.aliyuncs.com`, which answers in one request:

```
dev.zip  346,207,293 bytes  sha256 cdd6d19f…a60cf5a630  HTTP 200, last-modified 2024-06-29
```

So the block was never data availability. It was a probe of one host generalised into a property of
the environment, and the sixteen questions about it were answerable in four minutes. This file is
the correction: it measures the cell on the split the cell was measured on.

## What is being measured

`minidev` filters the 925 questions marked `simple`, because a question answered without memory
carries no signal for a transfer experiment. `dev` does not filter, because the sample size *is*
the claim: a published 53.52 on 1,534 questions can only be reproduced on 1,534. The same filter
that is right for one question is a protocol violation for the other, so the filter belongs to the
split — `poolOf(rows, split)` — and a test asserts both behaviours.

## What this run costs, measured before it was dispatched twice

The first dev dispatch finished fold 1 of 5 in 93 minutes and then printed its own forecast:
**the run needs about 12,037 calls; the cap is 8,000**. A fold on dev learns from 1,227 questions
for about 1,227 calls, five times over, and that — not the evaluation — is the cost of the split.

So this run caps the learning sample at **64 questions per fold** and says so in the artefact
(`config.learn_sample`). The evaluation is unchanged and complete: 1,534 questions, both arms, five
folds. What is reduced is the store the `full` arm reads, and the reduction is recorded rather than
implied, because a store built from 64 questions is not the store the flywheel readings describe and
a reader comparing the two would be comparing two different treatments. Prediction 4 below is written
against that reduction, not against the full flywheel.

Budget: 5 x 64 learning calls + 1,534 x 2 evaluation calls + retries, about 3,800 in total, which is
the number the run is dispatched with.

## Prediction

- The `none` arm answers all 1,534 questions and lands within the 7.72pp band that `compareCell` requires for a same-split comparison: roughly **51 to 56** percentage points.
- The verdict against `xiyan-deepseek-ddl` becomes `reproduced` rather than `indicative`, because the split names now match and the difference is inside 1.96 standard errors of each estimate added.
- The interval narrows as the square root of the sample: the Wilson band on 1,534 questions is about **±2.5pp**, against ±5.2pp on 350. That is the whole return on the run — not a better number, a cheaper one.
- The `full` arm does not turn positive on the larger sample. R9 measured memory at +1.33pp on 350 questions against a floor of +0.05pp with a 2.27pp cross-database penalty; if the sign is a property of the mechanism rather than of the sample, it survives 1,534. This arm reads a store built from 64 questions a fold, so a null here is weaker evidence than the R9 reading and will be reported as such rather than as a confirmation.
- The instrument holds: `data ok` is printed for all eleven databases before the first call, gold execution succeeds on every question, and no question is evaluated twice.

## Refutation

- If `none` on dev falls outside 53.52 ± 7.72, our harness is not measuring the quantity the published cell measures, the `indicative` verdict was generous rather than conservative, and every cross-paper comparison in this repository is withdrawn until the discrepancy is explained.
- If the `full` arm is significantly positive on dev — an interval excluding zero, not a point estimate above zero — then R9's closing condition ("memory is a lookup and not a lesson") is a property of the 350-question slice and R9 reopens with this artefact as its first evidence.
- If the answer rate is below 95% or gold execution fails on more than 1% of questions, the run measures the harness and not the model, and no number from it may be quoted regardless of direction.
- If the dev archive cannot be verified against its digest on a runner, the reproduction is blocked for a reason this file did not anticipate, and the honest output is `blocked`, not `pending`.

## What this does not settle

It does not compare memory to XiYan. XiYan publishes no memory arm, and the `full` arm here is ours
alone. What it fixes is the one cell in the comparison table that was labelled with a footnote
instead of a number.

## Amendment, written before the fifth dispatch

The fourth dispatch ran three folds and was killed by the step timeout at 160 minutes. Its log is the
reason this section exists, and the reading is arithmetic rather than interpretation:

| Fold | Evaluation | Learning + distillation |
|---|---|---|
| 1 | 614 replies in 2m07s | 3m47s |
| 2 | 614 replies in 1m45s | **43m02s** |
| 3 | 614 replies in 2m00s | **never printed** — killed 107 minutes later |

Two defects, both in the instrument.

**The client killed requests that were succeeding.** `LlmClient` waited a constant 60 seconds per
attempt whatever `max_tokens` asked for. Distillation asks for 2,000 tokens, which at the provider's
own throughput is more than a minute of generation; the reply was aborted, retried, aborted again,
four times, and then recorded as a prompt the model could not answer. Twenty-four corrections at
roughly two and a half attempts each is 43 minutes, which is the second row of the table exactly. The
attempt timeout is now `25s + 140ms/token`, capped at 300s — 53s at 200 tokens, 300s at 2,000 — and a
timed-out attempt is retried **once** instead of three times, because repeating a request the client
itself killed buys the same slowness and no evidence. The new `timeouts` counter separates the two
kinds of retry in the artefact.

**A killed request and a silent fold were indistinguishable.** A failed generation was cached as an
empty string and a failed distillation was counted as "the model said nothing". A fold whose store
was built from part of its corrections would have published a number. Three changes:

- `learn()` and the distillation adapter print progress, so the half of a fold that has no other
  voice is visible while it runs.
- The lane holds its own deadline (`SOTA_DEADLINE_MIN`, 130) below the step timeout (now 200), and a
  run that reaches it writes the folds it completed with `stopped_by: deadline` instead of being
  killed with nothing.
- **`V32-fold-learning-intact`** fails a run in which more than 10% of the learning questions went
  unanswered or more than 10% of the corrections failed to distil. This gate is declared here, before
  the dispatch, and it can invalidate the cell: a store built from 57 of 64 questions is not the
  treatment prediction 4 above is written against.

Neither change moves a prediction. What they change is whether a run that cannot answer its question
says so.

**Distillation is now paid concurrently** (`SOTA_DISTILL_CONCURRENCY`, 8): the batch is still applied
in corpus order, because a claim's effect depends on what is already in the store, but the prompts
depend only on their own events, so the round trips overlap. The measured consequence, if the
diagnosis above is right: a fold's learning half should fall from tens of minutes to a few.
