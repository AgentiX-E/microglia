# R33 — what ships, when the filter is the only part that pays

## Why this file exists

§146 measured the memory as a cost out of sample and the gate as a partial recovery of it. §147 then
split the same corpus by what memory did and priced the gate against the ceiling it could reach: the
gate removes 548 questions to prevent 36 net errors and realises 15% of the 3.39pp a perfect filter
would be worth.

That leaves three shapes and no evidence for choosing between them:

1. ship the filter alone, as a validity check on any generated statement;
2. ship memory with the filter and state the −0.20pp;
3. test a weaker injection to raise the repair rate.

Shape 2 is now bounded above by a wash — a perfect filter can only remove breaks, never add a repair —
so it is not a measurement problem, it is arithmetic. Shape 3 would have to move the exchange rate, and
nothing measured so far suggests a dose that raises repairs without raising breaks. **Shape 1 has never
been measured at all**, and it is the only one that does not depend on the rules being worth anything.

The filter's public definition is *discard a generated statement that imports a name the request never
implied*. Every measurement of it so far has been of the difference between two statements — the bare
attempt and the memory-served one — so what has actually been shown is that **the diff** carries the
signal. Whether the *query* carries it has not been tested, and those are different claims: a query can
name a column nobody asked for while the diff is empty, and a diff can add a name that the question
under-grounds only because the tokeniser and the question disagree about morphology.

This stage costs no model call. `per_case` in both committed artefacts stores the bare query
(`baselineSql`) and the served one (`predictedSql`), so the question-only rule can be evaluated against
both, on both splits, from data that already exists.

**What makes this a registration rather than an analysis** is that the outcome decides a product. The
rule, its anchor and the bar it has to clear are fixed below, before the number.

## The rule, stated so it cannot drift

For a query `q` and its question text `t` (plus the evidence block, which a solver may read):

- take every table and column name `q` uses;
- drop the ones the text grounds, under the stated rule — `strict` compares the identifier and its
  whitespace-separated parts against the text's tokens; `morphological` additionally accepts a prefix
  or containment match on de-underscored forms, which is what recognises `movieid` in *movies*;
- the query is **flagged** when what remains is not empty.

Both rules are reported. `strict` is quoted as the primary because it is the rule §140–§147 have used
everywhere else; `morphological` is reported beside it because it is the only honest candidate for a
question-only anchor, and a reading that chose one rule after seeing both would be the thing this file
exists to prevent.

Three quantities are registered, each on both splits:

| quantity | definition |
|---|---|
| **flag rate** | share of attempts the rule flags |
| **gap** | accuracy among flagged minus accuracy among clean, resampled over databases |
| **J** | Youden's index, `P(flag \| wrong) + P(no flag \| right) − 1` |

**The bar for J is 0.107**, and it is not arbitrary: it is the memory filter's own Youden index on the
out-of-sample corpus, `76/237 + (187−40)/187 − 1`. The question-only check has to be at least as good a
discriminator as the diff-anchored one before it can be proposed as a replacement for it.

## Prediction

- **P1 — the instrument is intact.** Both committed artefacts load, `per_case` joins to 7,000 train and
  1,534 dev cases, and every case carries a non-empty `baselineSql` and a non-empty `predictedSql`.
  A run in which either column is empty has measured the parser, not the check.
- **P2 — without a baseline the rule fires on most attempts.** The strict question-only rule flags at
  least **60%** of bare attempts on train, and the morphological rule at least **40%**. Expect the
  strict number to be above 85%: with no baseline to subtract, every legitimate column whose surface
  form differs from the question's wording counts as imported, and the anchor is the whole reason the
  filter looked precise. This is a prediction about the *rule*, not about the model.
- **P3 — even so, the flagged attempts are worse.** Accuracy among flagged bare attempts is at least
  **5pp lower** than among clean ones on train, with a clustered interval that excludes zero. A flag
  that fires on most of the corpus can still separate within it, because the wrongness base rate is
  41.8% and a query that names something unasked-for is a query that has committed to a schema detail
  the question did not supply.
- **P4 — the same sign on dev, at a similar size.** Dev's gap is negative, and within **4pp** of
  train's. A gap that exists on one corpus and not the other is a property of the corpus, and this
  record has already spent a round learning what that costs.
- **P5 — the question-only check clears the memory filter's bar.** Youden's J for the flagged-bare
  reading is at least **0.107** on train and on dev. Expected value **0.20–0.30**: the target is
  "this attempt will fail", which is 41.8% of the corpus and mechanically related to how the query was
  written, not "the rules will damage this attempt", which was 3.4% and only weakly related.
- **P6 — the pack still adds names, measured without the baseline anchor.** The flag rate on the
  served query exceeds the flag rate on the bare query by at least **5pp** on train. This is §146's F1
  reproduced under a second, independent rule; if it does not reproduce, the imported-name finding is
  an artefact of the baseline anchor and §146 must be re-read.

## Refutation

- **P2 fails and P3 fails**: the question-only rule neither fires broadly nor separates. Then the
  filter's value is the *diff* and not the *query*, §146's "the filter is a property of the query, not
  of the rule" is only half true, shape 1 dies, and R33 closes with no product rather than with a
  weaker one. This is the outcome that ends the product line, and it is written here first because it
  is the one that will feel like a failure while it is being concluded.
- **P2 holds and P3 fails**: the rule is firing on surface-form noise. Then the fix is a better
  tokeniser rather than a better product, and shape 1 is deferred rather than refuted — with the
  deferral conditional on a pre-registered tokeniser change, not on a search.
- **P3 and P4 hold but P5 fails** (J below 0.107): the check works and is worse than the filter it
  would replace. Shape 1 becomes "ship the filter with memory, and pay the −0.20pp for the check" or
  nothing; there is no third option where the check alone earns its place.
- **P5 holds with J clearly above 0.107**: shape 1 is the product, and the next stage is an *abstention*
  arm — flag, do not answer, or retry once — measured against a no-memory control. That is a different
  product from the one this programme has been building, and it is the one the evidence would support.
- **P6 fails**: the imported-name finding does not survive a second rule, and §146–§147 need a
  correction before anything downstream of them is quoted.
- **Abandonment rather than reinterpretation.** If the flag rate on either corpus is below 5% under
  both rules, there is nothing to trade off and the stage is abandoned rather than re-specified: a
  check that almost never fires is a check that cannot cost anything and cannot be worth anything.

## Amendment 1 — ten rows out of sample carry no bare query

Written on 2026-11-01, after `V53` refused the corpus and before any verdict in `poc-validity.json`
was read.

`V53` as registered asked that every case carry both queries. The artefact does not: 12 of 7,000 train
rows are missing one. **Ten are missing `baselineSql`** — the bare attempt — and are otherwise ordinary
rows: parseable, executed against the database, and recorded as wrong in the bare arm. **Two are missing
`predictedSql`** and are the parse failures the run already records as `parseOk: false`.

The ten are a defect in the source artefact rather than in this reading. A query that was never stored
cannot be shown to a rule, and no amount of analysis recovers it. Two consequences, both stated before
the numbers were read:

1. **P1 is restated.** "Every case carries both queries" is refuted by the artefact. It becomes: both
   corpora load at the registered sizes, and every missing query is one the run already records as a
   failure. `V53` polices exactly that — a row missing a bare query must be `withoutMemoryCorrect:
   false`, and a row missing a served query must be `parseOk: false`. Both hold on both splits, so the
   ten absences are consistent with the arm they belong to, and none of them claims to be an answer.
2. **A case with no query is excluded from the arm it is missing from**, and the count travels with the
   reading as `excluded`. The alternative — counting it as unflagged — puts a known failure into the
   clean group and biases the gap toward zero, which is the direction that hides a result.

The readings under both treatments, so the choice carries its own price tag:

| treatment | gap, train | clustered | Youden |
|---|---|---|---|
| the 10 counted as unflagged | −10.71pp | [−21.58, +0.44] | 0.0224 |
| the 10 excluded (registered) | **−12.58pp** | **[−22.15, −2.92]** | **0.0257** |

The exclusion changes the verdict on **P3** — the interval covers zero under the first treatment and
excludes it under the second — and it does not change the verdict on **P5**, which is the one that
decides the product. That asymmetry is the reason to publish both columns rather than the convenient
one, and it is also the reason the exclusion is not a licence to re-read the corpus: it is a rule about
a missing input, applied to a predicate that is not defined without one, and it would have been the same
rule had the gap moved the other way.
